## 四、P1-1：`.kb/state/` 状态检查点（本次最大发现）

```
.kb/state/checkpoint.1.jsonl    152.1 MB   101 行   1 天前仍在写
.kb/state/checkpoint.2.jsonl    146.1 MB   101 行   2 天前
.kb/state/checkpoint.3.jsonl    138.1 MB   101 行   3 天前
.kb/state/checkpoint.jsonl       56.5 MB    37 行   当天
.kb/state/reverse_index.json     59.0 MB          当天
                        小计 ≈ 552 MB
```

- **性质**：KB Vault MCP 服务的会话检查点。`checkpoint.N.jsonl` 是历史轮转备份，实际只有最新的 `checkpoint.jsonl` 在使用。
- **问题**：只增不减，**单个 101 行文件就 152 MB**（每行一个全量状态快照）。照此速度，再攒几轮就会突破 GB。
- **成因**：检查点写入采用全量 append，没有轮转上限、没有压缩。
- **建议**：
  1. 先只保留最新一份，把 `.1/.2/.3` 移入 `.kb/state/_archive/` 观察几天确认服务不读，再删——**可释放 ~436 MB**。
  2. 根治：给 MCP 服务加检查点轮转上限（如最多 2 份）或改用增量写入。这一步需要改 `kb-vault-mcp/` 的配置/代码，**建议单独开工单**。
- **注意**：这些文件 0–3 天前仍在被写，说明服务在运行。**不要在服务运行时直接删**，先停服务或先归档。

## 七、执行提醒（Windows 特有）

按既有经验，在本机做删除时必须注意：

1. **删除 ≠ 释放空间**——文件会进回收站，占用不变。删完必须清回收站并复查：
   `Clear-RecycleBin -DriveLetter C -Force`（PowerShell 专用），随后用 `df -h /c` 复核。
2. **当前磁盘确实偏紧**：本次实测 C 盘 **454G 中已用 384G（85%），仅剩 70G**。这是本次清理值得做的现实依据，也意味着释放 ~660 MB 有意义但不解决根本问题——若要显著腾空间，真正的目标是 §一表格里的 PDF 5.25 GB 与 DOCX 1.2 GB，但那属于资产权衡，需单独决策。
2. **先归档观察，不要直接删**。本报告所有建议的默认动作都是「移入 `_归档/`」而非删除。
3. **分批小量**：每次 ≤10 个文件，验证后再继续。
4. 清理前确认没有并行会话正在读写这些路径。
