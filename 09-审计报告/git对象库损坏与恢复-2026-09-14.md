# git 对象库损坏与完整恢复（2026-09-14）

> 结论先行：**已完整恢复，零历史丢失**。`git fsck` 全绿（missing 0 / broken 0 / error 0），
> 本地 `master` 与 `origin/master` 同为 `65bddb779`。工作区文件**从未受损**。

## 一、现象与发现时间

- 22:45 前后起，`git status / diff` 报 `fatal: bad object HEAD`；
  `git cat-file -t HEAD` 报 `could not get object info`。
- 此前同一会话内 `git status / log / diff` 均正常 → 损坏发生在 **22:44~22:46** 窗口内。

## 二、诊断过程（每一步都可复现）

| 步骤 | 命令 | 结果 |
|---|---|---|
| 1 | `git rev-parse HEAD` | `65bddb779…`（引用文件可读） |
| 2 | `git cat-file -t HEAD` | **失败** → commit 对象本体缺失 |
| 3 | `git count-objects -v` | 4 packs / in-pack 173924 / 松散 5845 |
| 4 | 逐 pack 抽样 `git show-index` + `git cat-file -t` | **4 个 pack 全部健康**（各抽 40~43 个对象 100% 可读）→ 损坏不在 pack |
| 5 | `grep gc.* .git/config` | `gc.auto=0`、`maintenance.auto=false` → **不是自动 gc 干的** |
| 6 | `git fsck --connectivity-only` | **missing 3511 / broken 167 / dangling 802**（3357 blob + 141 tree + 13 commit） |
| 7 | 找不到对象文件：`.git/objects/52/efc2859f…` 不存在，且不在任何 pack | 松散对象被**移除**而非损坏 |

## 三、根因：沙箱 `safe-delete` 把 git 松散对象移进了回收站

排查线索：WorkBuddy 沙箱对 `rm` 有 `safe-delete` 拦截（本次实测 `rm` 一个 tmp pack 时报
`[safe-delete][SAFE_DELETE_FAIL_CLOSED] … trash-failed`）。据此检查回收站：

```
C:\$Recycle.Bin\S-1-5-21-…-1001\   6295 个文件 / 1.5 GB
```

解析 6321 个 `$I` 元数据（8 字节头 + UTF-16LE 原始路径），其中 **4893 条**的原始路径正是：

```
C:\Obsidion\妙妙屋\.git\objects\75\37cb3c8f863c806213fa42efe5aee0ec297553
```

→ 结论：**这些对象是被「移到回收站」而不是真删除**（内容 100% 完好）。
随机抽样验证：该文件 zlib 解压得 `blob 4898`（JPEG），实算 SHA1 = `7537cb3c…` 与路径完全一致。

## 四、恢复（三步，全部无损）

| 来源 | 数量 | 方法 |
|---|---|---|
| 回收站 | **4892** | 解析 `$I` 取原始路径 → `$R<bits>` 复制回 `.git/objects/XX/YYY` |
| 工作区重算 | **324** | 缺失 blob 若与索引内现存文件内容一致 → `git hash-object -w`（内容寻址，SHA 必然相同） |
| 远端补取 | **100** | 启用 promisor 后用 `git cat-file -t` 逐个触发按需拉取（102 个里 1 个是解析噪声、1 个是 SSL 瞬时错误，重试成功） |

关键一步：**过滤式全量补取**补齐了 3 个缺失 commit 与 33 个 tree

```bash
git fetch --refetch --filter=blob:none origin master   # 230MB，几分钟
```

为什么必须过滤：普通 `git fetch` 要做「共同祖先」协商，而协商要遍历本地历史，
一碰到祖先链上的空洞（`28fe536d`）就 `Could not read …` 直接失败；
`--refetch` 不做协商 → 绕开空洞；`--filter=blob:none` 只取 commit+tree → 体积从 ~2.9GB 降到 230MB。

## 五、收尾与验证

```bash
git config --local --unset remote.origin.promisor
git config --local --unset remote.origin.partialclonefilter   # 不留 partial-clone 配置
git fsck --no-progress    # EXIT=0，missing 0 / broken 0 / error 0（仅 3 个 dangling，正常）
git rev-list --count HEAD # 526（祖先链完整）
```

> ⚠️ **promisor 会制造假绿**：在 promisor 未取消时 `fsck` 把缺失 blob 视为「已承诺」而报 0 缺失。
> **必须取消 promisor 后再跑一次真实 fsck**（本人就踩了这一次）。

## 六、教训

1. **`.git/` 内的删除会被沙箱拦截并移入回收站** —— 好消息是「丢」可恢复；
   坏消息是 git 自己的 unlink（prune/cleanup）也可能被这样拦截，使仓库**静默**受损。
   → **回收站是本环境的第一恢复源**：`.git/objects/XX/YYY` 的原始路径完整保存在 `$I` 里。
2. **`git fetch --refetch --filter=blob:none` 是「历史有空洞」时的标准解法**：
   不做协商 → 绕开空洞；只取 commit+tree → 体积可控。
3. **先证伪再下结论**：pack 是否健康要用「抽样 `cat-file -t`」证明，不能只看 `count-objects`
   （09-13 曾出现「对象数少、体积大」的畸形 pack，与本次「pack 全健康、松散对象被移除」是**两种不同故障**）。
4. 本次**未使用** `gc / repack / prune / prune-packed / reset --hard`，全部操作可逆。
