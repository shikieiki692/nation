# 妙妙屋日常操作模型

> 基于 2026-05-05 至 2026-07-27 共 84 天、50+ 份工作日志、55KB 经验沉淀、1.5 万字 SOP 的全面分析。

## 一、系统全景：五层架构

"人+AI协作操作系统"分五层，每层解决一个核心问题：

| 层级 | 核心文件 | 解决的问题 | 比喻 |
|:---|:---|:---|:---|
| 方向层 | Agent战略方向 | "往哪走" | 导航仪 |
| 执行层 | Agent最小执行协议 + 任务分解指南 | "怎么做" | 操作手册 |
| 路由层 | task_type 路由表 + 11个Agent提示词 | "谁来做" | 调度中心 |
| 方法论层 | 多源资料整合 + 题集构建工作流 + 讲义生产SOP | "做得对不对" | 质量标准 |
| 记忆层 | 会话交接 + 经验沉淀 + 工作日志 + 状态摘要 | "之前做了什么" | 长期记忆 |

五层之间通过"任务卡"连接。task_type 字段是路由核心——Agent 不再自行猜测该读什么，而是由任务类型精确路由到"读什么+用什么提示词+收工同步哪里"三件套。

## 二、每日操作的四个阶段

### 阶段 1：启动（5-15 分钟）

用户下达指令后，Agent 按以下顺序加载上下文：

1. 读状态摘要（会话快照）
2. 读活跃任务（当前任务卡 + 健康检查）
3. 读 Agent战略方向（长期优先级）
4. 如有会话交接，检查最新交接笔记
5. 创建或认领任务卡
6. 判断 task_type，路由到对应提示词

实际操作中的变体：日常小任务只读状态摘要（10秒）；标准任务读三入口文件（2分钟）；跨模块大任务升级到完整模式读8文件（5分钟）。

### 阶段 2：执行（30 分钟至数小时）

这是核心工作阶段。从日志中提取出六种反复出现的操作模式。

**模式 A：批量构建**（最常见，约占 40% 操作量）

典型流程：标杆样本验证（1-2个文件试做） -> 用户确认格式/方向 -> 并行Agent批量执行（5-11个Agent，每批10-20文件） -> 抽查验证（3-5个文件） -> 问题修复 -> 再验证。

典型案例：05-05 日 113个KP并行填充 + 322道题入库；05-25 日 484个KP模板迁移（11个并行Agent）；07-23 日 32个骨架KP填充（两批并行）。

**模式 B：审计-修复螺旋**（第二常见，约占 25%）

典型流程：全量扫描/审计 -> 发现问题分类（P0/P1/P2） -> 批量修复P0/P1 -> 再扫描确认 -> 仍有残余则继续修复 -> 直到达到阈值。

典型案例：07-22 日 validate_kb 从 492 warning 降到 0 error / 14 warning；07-23 日断链从 6494 降到 5587 再到 5601（螺旋收敛）。

**模式 C：模板/SOP 实战迭代**（贯穿全程）

典型流程：实战中发现模板/SOP缺陷 -> 现场修补 -> 沉淀为新版模板 -> 新版投入下一轮实战 -> 再发现缺陷。

典型案例：SOP 从 v1.0 到 v1.5.7（17次版本迭代）；学生讲义模板从 v1.0 到 v1.2.2。

**模式 D：备课驱动的内容深化**

典型流程：备课大纲生成 -> 发现KP不够深或不够用 -> 回头深化KP + 补配图 + 补例题 -> 产出讲义（自学版+课堂版） -> 反哺KP（课件中关键图回填） -> 聚合到专题页。

**模式 E：技术债清偿**

典型流程：发现基础设施问题（编码/格式/工具兼容） -> 编写修复脚本 -> 全库执行 -> 验证零残余 -> 沉淀为工具或SOP规则。

典型案例：05-25 日 48文件GBK编码损坏修复；07-22 日 kb-vault-mcp Windows兼容性修复（10个源文件重写）；07-23 日 3226个md文件CRLF/BOM统一。

**模式 F：灾难恢复**（罕见但影响大）

典型流程：发现数据损坏或误操作 -> git历史恢复 -> 分析根因 -> 写入经验沉淀（通常标记三个火焰） -> 建立防护机制。

### 阶段 3：验证（10-30 分钟）

固定检查清单包括：frontmatter 完整性、wiki-link 有效性、编码完整性、跨系统连接（提炼与KP与专题页与备课框架四向链接）、内容准确性（抽样）。

关键发现：验证阶段从未一次通过。每次验证都会发现新问题，触发"修复到再验证"螺旋。这是系统的常态而非异常。

### 阶段 4：收工（15-30 分钟）

SOP 定义了收工九必做：写工作日志、更新任务卡、更新索引、同步状态摘要、同步Agent战略方向、同步备课待办、写会话交接笔记（15行内）、历史Follow-up回填、给用户交付总结。

从日志看实际执行情况：收工阶段经常被压缩或跳过，导致后续出现"状态漂移"。这正是 SOP v1.4.8 强化收工同步的原因。

**代表性对话**：

用户说"启动路线A1"，Agent执行28届初赛拆题产出33个单题文件。用户说"继续32/33届"，Agent连续执行。用户说"36-38届也一起做"，Agent 4个源文件并行拆题。用户最后说"做一个小结，暂时结束"，Agent输出跨会话交接文档。

### 类型二：教材资料提炼到知识点填充（双Agent协作）

代表日志：2026-05-15（Atkins物化7个主题）、2026-05-18（Weller+Clayden+超分子）

**用户指令**："帮我提炼Atkins物理化学第5章，然后把相关知识点填充好"

连续处理7个主题，每个主题都是"提炼到填充"双循环。

**代表性对话**：

用户说"帮我导入并提炼30-33章吧，注意图片的引用"。Agent产出4份提炼笔记 + 2个KP新建 + 2个KP深化。新建"环状分子的立体选择性"（5张图嵌入）和"非对映选择性"（5张图嵌入）。

用户说"超分子不导了，重要性不高，进行全库状态审计吧"。Agent立刻停止超分子导入，转入审计模式。发现28个KP状态标签与实际内容不符。批量修正28个文件，全库568/568已填充、0骨架。

用户说"中等动作，内容不需要太多，不是重点"。Agent全部轻量填充，精简为核心定义加关键结论。

**编码灾难（2026-05-23）**：Bases仅显示446条知识点记录，与预期约701 KP严重不符。深入扫描发现331/702个文件存在UTF-8替换字符，总计约86,837处。原因：Agent/脚本在批量操作时使用了不兼容的编码（GBK vs UTF-8）。修复：编写fix-encoding-v2.js（约250条替换规则），从5.19备份恢复26个严重损坏文件。乱码从86,837处降至0。

**并行写入数据损坏（2026-05-25）**：48个有机化学文件编码损坏，21,960个乱码字符。原因：第四批并行Agent批量迁移v1.1 KP时，多个Agent并行写入导致编码混合。无git备份，部分数据永久丢失。

## 七、总结

你做的事情是：把一个化学竞赛教师的全部备课资产（教材提炼、知识点、题库、讲义、专题）组织进一个Obsidian知识库，然后用AI Agent帮你做数据管理、质量审计、内容生成和跨会话记忆——你做教学判断，AI做繁重操作。

你的操作系统不是一次设计好的，而是84天里"实战到踩坑到沉淀到制度化"螺旋迭代出来的，经历了构建、规范、治理、优化四个阶段。

最核心的设计决策是：任务卡驱动（而非文件驱动）、源派生分离（Single Source of Truth）、和"每次踩坑产生一个永久防护"的自进化机制。

最深刻的教训是：灾难性故障（3起编码和清理事故）教会了系统"永远用git、永远先备份、永远不信任批量操作"；产出质量不足（12起用户不满）教会了系统"充实的标准由用户定义、不由Agent猜测"。
