## §4 红线与本次事故的硬教训

1. **`.git/objects/` 的删除会被沙箱移入回收站**（不是真删除）→ 任何「对象丢失」先去
   `C:\$Recycle.Bin\<SID>\` 找：`$I*` 元数据（8 字节头 + UTF-16LE 原始路径）里存着
   `.git\objects\XX\YYY`，同名 `$R*` 就是内容。**本次靠此零丢失救回 4892 个对象。**
2. **本仓库 `fsck` 不可信**，判据用 `git cat-file -e`（09-13 已定论）。
3. **promisor 会制造假绿**：未取消 promisor 时 `fsck` 把缺失 blob 当「已承诺」报 0 缺失。
   取消后必须重跑一次真实 `fsck`。
4. **`git fetch <sha>` 在本仓库属红线**（09-13 记录会制造畸形 pack）。本次我在未读该红线前跑过两次，已如实记录。
5. **长任务/推送一律后台**（本机推送单次 4~9 分钟，前台会被 SIGTERM）。
6. **`git fetch --refetch` 全量重取在本仓库不可行**：09-14 实测跑 1 h 4 m 后以
   `early EOF` / `invalid index-pack output` 失败（体积 3 GB+ / 网络中断），并残留 773 MB 孤儿 `tmp_pack_*`（沙箱拦删除）。
   判断「与远程是否同步」一律用 `git ls-remote origin master` 比哈希；**不要靠 refetch**（对象库本已健康、无需重取）。
